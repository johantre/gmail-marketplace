# Sprint Review Marketplace — projectcontext voor Claude Code

Dit document is de overdracht van een ontwerpgesprek naar implementatie.
Lees dit volledig voor je iets aanpast — de "waarom"-kolom bevat beslissingen
die al overwogen en verworpen zijn; heropen die discussie niet zonder aanleiding.

## Doel

Sprint Review in Marketplace-formaat: meerdere topics, elk met een eigen
kraampje/desk. Nodig:
1. Vooraf weten wie in welk topic geïnteresseerd is (aantallen per topic).
2. Tijdens de sessie: bezoekers vinken zelf af welke topics ze al bezocht
   hebben, zodat er live zicht is op "hoeveel nog te gaan" per topic.
3. Eén klik om per Review-cyclus: een inschrijfformulier te (re)genereren,
   een PO-presentatie te genereren, en de checklist-QR te tonen — zonder
   ooit code aan te raken. Topics/desks wijzigen = een rij in een
   configuratietabel aanpassen. De presentatie heeft vrije intro-/eindslides
   in Acme-stijl (marketing's domein, code raakt ze niet aan) en één
   topics-lijst-slide die zichzelf automatisch over meerdere pagina's
   verspreidt als er te veel topics zijn voor de voorziene ruimte.
4. Herbruikbaar: Sheet, Form en Slides-template blijven permanente
   mother-artifacts over alle Reviews heen (zie architectuurtabel — dit
   verving op 2026-08-14 de eerdere "kopie per Review"-aanpak). Na afloop
   van elke Review worden enkel de resultaten (Aanmeldingen, Dashboard,
   Form-antwoorden) gearchiveerd naar een apart archief-Spreadsheet en
   gereset voor de volgende cyclus.

## Huidige stand van de implementatie

**[HERSTRUCTUREERD op 2026-08-15]** `Code.gs` was uitgegroeid tot ~2000 regels
en is nu opgesplitst in 13 bestanden naar verantwoordelijkheid, één bestand
per keer geëxtraheerd en telkens live getest (`runSelfTests` + een gerichte
functionele test) vóór de volgende stap. Apps Script deelt nog
steeds ALTIJD één globale scope over alle `.gs`-bestanden heen (geen echte
modules/imports) — de opsplitsing is dus puur voor leesbaarheid/navigatie,
geen architecturale scheiding. Eén concrete valkuil die de opsplitsing wél
moest omzeilen: `getInstellingenSeedRows()` (in `Sheets.gs`) is bewust een
FUNCTIE, geen top-level `var`-array, omdat ze verwijst naar top-level
constanten uit andere bestanden — Apps Script voert top-level code uit in
editor-lijst-/`filePushOrder`-volgorde, niet gegarandeerd alfabetisch, dus een
top-level array-literal die naar een constante uit een ander bestand
verwijst zou breekbaar zijn. Functiedeclaraties zelf zijn wél altijd veilig
ongeacht bestandsvolgorde (gehesen over het hele gecombineerde script).

Bestanden in de Bitbucket-folder:

- `Code.gs` — nu enkel een **index/overzicht**, geen logica meer: het
  bovenaan-in-het-project-commentaar met de "One-time settings"-documentatie

## Verwachte kolomstructuur "Aanmeldingen" (contract met de code)

```
Timestamp | E-mail | Interesse (ruw) | Interesse_<topic1> | Bezocht_<topic1> | Interesse_<topic2> | Bezocht_<topic2> | ...
```

Geen `Naam`-kolom meer sinds 2026-08-15 (zie architectuurtabel) — e-mail is
de enige echte key, `Naam` werd nergens gelezen. Een reeds-bestaand
`Aanmeldingen`-tabblad van vóór deze wijziging behoudt zijn oude
`Naam`-kolom fysiek (niets in de code verwijdert bestaande kolommen) — die
blijft gewoon leeg voor nieuwe inschrijvingen; manueel verwijderen is
optionele opruiming, geen vereiste.

`Interesse (ruw)` = de comma-separated tekst van de geselecteerde
checkbox-labels (`Topic (Desk)`), weggeschreven door `onFormSubmitHandler`.
De `Interesse_<topic>`-kolommen zijn **waarden, geen formules**: berekend bij
inschrijving door een exacte match tegen de checkbox-labels van dat moment
(zie architectuurtabel bovenaan — bewuste keuze i.p.v. `ISNUMBER(SEARCH(...))`
zoals in de vroegere `marketplace_tracker.xlsx`). `Bezocht_<topic>` start op
`false` en wordt nadien enkel via de checklist-webapp (`setBezocht`)
aangepast. Kolommen worden door `syncAanmeldingenColumns()` aangemaakt/
aangevuld op basis van Config — nooit manueel toevoegen of hernoemen.
